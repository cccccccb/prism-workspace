# 参考图驱动的视觉与平铺主线

日期：2026-09-26。状态：代码差异审查与实施规范，以下新增能力尚未实现。

本计划承接 Skia 应用迁移和 Pi deb 演示。用户现场确认“画面正常”表示显示链路工作，不能据此认定视觉目标已经完成。用户本次提供的参考图确定新的外观验收依据。

## 1. 参考范围与目标

参考播放器画面内部桌面区域的玻璃顶栏、悬浮图标 Dock、柔和边缘与层次。保留当前壁纸，不复刻 VLC 标题栏、播放器控件或图中人物内容。

- Topbar：薄玻璃面板，左右控制区，时钟相对整个栏真正居中；窄屏时两侧内容让位，不能挤走时钟。
- Dock：底部居中的悬浮圆角面板，与屏幕边缘有距离；应用抽屉、分割线、真实图标卡片、运行指示和悬停反馈。
- 应用窗口：采用 i3/Sway 式容器树分割；支持横向、纵向、嵌套、焦点与工作区。窗口间留缝，边框、圆角、内阴影与外阴影形成层次。普通模式的窗口不互相任意覆盖，拖拽改变拓扑或分割比例。
- Shell 不进入应用平铺树；工作区可用范围依据 Shell 的实际布局与保留区域统一计算。
- 首版主题建议：Topbar 高 30–34 逻辑像素、边缘留白 8–12；Dock 图标 44–48、面板高 64–76、底部留白 10–14；应用 inner gap 10–14、outer gap 12–16、圆角 10–12、边框约 1。这些是待实机校准的主题参数，不能成为 WM 中散落的常量。
- 窄屏 Dock 首版使用明确的 overflow/滚动策略；不能逐项裁短图标。图标、文字与点击区域均需适配当前 1024×600 输出。

## 2. 当前代码与目标差异

以下依据当前安装所对应的生产模板和实现审查；用户本次附件是目标图，并非当前屏幕截图。

| 范围 | 当前实现 | 需要补齐 |
| --- | --- | --- |
| Topbar | `prism-topbar/ui/topbar.prism`：固定宽度的一行文字/按钮、纯色底 | 左中右分区、全栏居中、图标、玻璃材料、留白 |
| Dock | `prism-dock/ui/dock.prism`：Apps/Files/Term 等文字按钮，72 高；WM 固定最大宽度 800，贴屏幕底部 | 内容测量、悬浮边距、图标卡片、分割线、实际窗口运行状态 |
| 客户端布局 | `layout_engine.cpp`：简单行列分配、Box 子项叠放；缺少对齐、布局权重、明确的 intrinsic/overflow 语义 | 测量/放置语义、对齐、弹性空间、边距、受约束内容与溢出处理；不在本轮引入节点增量布局 |
| 透明呈现 | EGL 请求了 alpha 通道，但 `RasterRenderer::Replay` 清为不透明黑；SHM 诊断目标为 opaque | 明确 surface 清屏/alpha 契约，透明窗口透出真实下层；修复圆角外部黑底 |
| 本地视觉 | DisplayList 只有填充、圆角填充、图片、字形及矩形裁剪/变换 | 描边、圆角裁剪、内/外阴影、图标资源、图片 fit、基础控件状态 |
| 背景模糊 | 新客户端无 backdrop effect；旧装饰只有参数和矩形场景节点 | compositor 跨 surface 背景采样/模糊与效果提交契约 |
| 真窗口布局 | `ArrangeXdgViews` 按数组横向均分；topbar 38，但应用从 y=34 开始，存在 4 像素重叠 | 统一 Shell work area，真实 XDG view 接入 TreeEngine，删除第二套几何算法 |
| 窗口装饰 | 旧模型有主题、BSP、decorator；真实 XDG view 直接建 surface scene，未持有对应 managed Window | 真实窗口生命周期、装饰与焦点关联；已有矩形装饰也需补圆角/阴影/blur |
| 示例控件 | 音乐进度和播放操作等使用文字占位；设置示例主要是文字信息卡 | 真正的图标按钮、进度/Slider、Toggle 及状态反馈，业务仍归客户端 |

`DESIGN_SPEC.md` 第 10、12、15 节表达了目标，但其中部分“已完成”表述及旧启动/ImGui/AOT 示例属于历史设计；以 `APPLICATION_MIGRATION.md` 和实际代码核对实现状态。

## 3. 效果职责与解耦边界

### 客户端 SDK / Skia

DSL 属性解析、主题 token 解析、Scene 状态、测量与布局、文字/图标/控件、客户端自身图形的描边与阴影由 SDK 完成。效果按总体架构第 13–14 节进入独立 EffectState/Layer 语义，不在每种 geometry 或应用里重复实现。Skia 负责客户端本地效果回放。

主题使用一份定义产生客户端与 WM 所需的类型化配置；WM 不引入客户端 DSL/parser。使用相同参数名称、单位和版本，明确谁负责绘制每一种边框/阴影，避免 client 与 WM 重复叠加窗口框架。

### WM / compositor

WM 负责真实窗口树、Shell 放置、work area、surface 分层、焦点、装饰和跨 surface 背景效果。真实毛玻璃需要读取该区域下面的已合成内容，独立客户端的 Skia framebuffer 没有这些像素；模糊客户端自己的内容不能实现这一目标。

SDK 将已经解析并布局完成的 backdrop 需求转为平台层类型化请求，至少包含 surface 内区域、圆角、模糊尺度和提交关联。首版支持圆角矩形区域；WM 只接收效果数据，不接收 AST、控件树、应用动作或 DisplayList。私有 Wayland 扩展需单独定义版本、单位、能力协商和随 surface commit 生效的生命周期。

合成顺序：该效果区域下面的场景 → 扩展采样边界 → GPU 背景模糊 → 按圆角区域裁剪 → 客户端半透明 tint 与前景。不能采样本 surface 或更上层 surface。应用自身有不透明内容时，该内容仍会遮住下层材料，这是正常语义。

原生 `wlr_scene` 场景节点不能仅凭新增一个 `blur_radius` 字段完成上述流程。需要明确的 compositor GPU effect pass / 场景回放集成点，并验证导入、buffer 寿命与同步；不将客户端 Skia 和 DSL 搬回 WM。首版不默认替换 wlroots 版本，若需要修改依赖，先记录改动范围与维护成本。

窗口外阴影由窗口装饰层绘制在 tile 之外但不改变树的槽位；邻接间距、装饰绘制范围与输入命中区域需区分。圆角处客户端内容和输入区域应与可见轮廓一致。客户端局部卡片阴影则由 Skia 绘制；跨窗口 blur 与局部滤镜分别建模。

## 4. 执行顺序与完成条件

用户随后明确要求恢复统一启动与前端可控的平台目标。先完成 [LAUNCH_RUNTIME_RESTORATION_PLAN.md](LAUNCH_RUNTIME_RESTORATION_PLAN.md) 的包/host/预热服务与五应用切换门槛，再依次执行本节的视觉和平铺步骤。

### 第一步：统一真实窗口几何与 BSP

真实 XDG view 与纯窗口管理模型建立稳定映射，不伪造共享内存客户端或旧 IPC channel。map/unmap/destroy、焦点、工作区、关闭与 fullscreen 都更新同一窗口记录。TreeEngine 的目标几何驱动 configure，已提交的客户端尺寸与动画显示几何分别跟踪。

Shell 布局、保留空间与应用 work area 共用类型化配置。接通真实窗口的横/纵分割、嵌套、方向焦点、swap 和工作区可见性，删除按 view 数量横向均分的布局路径。普通单窗口的 gap 由主题决定，显式 fullscreen 的保留空间/装饰策略单独定义。

验收：2/3/4 个真实客户端可以嵌套分割，IPC tree 对应实际 surface；Shell 不占树节点；窗口不覆盖 Topbar/Dock，不出现旧模型和真实 view 的双焦点。

### 第二步：透明与通用布局契约

制定并实现 alpha 清屏、预乘格式、透明/不透明区域声明与圆角裁剪；同步修正 CPU 诊断目标，避免测试契约与 GLES 分歧。随后补足 measure/arrange、主轴/交叉轴对齐、flex、inset、intrinsic 与 overflow。文字布局要使用 shaping 的实际度量，不能仅用字号乘常数估计所有内容。

验收：圆角外真实透出壁纸，没有黑色矩形；时钟全栏居中；窗口变窄时内容遵循明确的溢出规则。

### 第三步：本地视觉与控件

按 Schema → Style/Effect → RenderTree → DisplayList → Skia 的顺序增加描边、内/外阴影、圆角 clip、图片 fit 和图标资源，再实现 IconButton、Separator、Progress/Slider、Toggle 的布局、绘制、命中与状态更新。图标和交互能力归 SDK，业务动作归应用。

验收：五个应用共享这些能力；无应用名分支；图标不是文字缩写/emoji 替代；控件状态与点击/键盘交互一致。

### 第四步：真实背景材料与窗口装饰

定义 surface effect 请求契约，接入 GPU backdrop pass、圆角窗口边框、顶缘高光、内阴影和外阴影。先验证静态 Shell 与真实窗口，再处理 resize/移动/下层内容变化产生的模糊区域更新。效果关闭时正常合成路径仍正确。

验收：保持背景细节的磨砂效果；下层内容变化会更新；窗口轮廓、阴影和命中一致；Pi 客户端与 compositor 都使用硬件驱动。模糊参数依据实测选择，不将历史 `passes: 4` 当作性能保证。

### 第五步：按参考图重排 Shell 和示例

统一主题 token，更新 Topbar、Dock 和示例模板。Dock 接入真实窗口列表/激活结果，不再把成功 spawn 次数当成全局运行状态。保持当前壁纸；桌面临时标题卡片按最终桌面布局规范移除。动效在基础布局/命中完成后接入，共用时间调度。

验收：1024×600 下左右状态区、时钟、图标和 Dock 留白正确；窗口拓扑仍符合平铺规范。保存同一输出尺寸的实际截图供参考图比较。

### 第六步：更新 deb 并重复实机验收

测试和捕获工具留在 `tests/`，不安装到生产目录。更新 deb 版本，验证安装资源和重启清理，再检查普通/聚焦窗口、分割、输入、缩放与玻璃效果。记录真实外观及性能数据；阶段完成状态分别标注，不能以映射成功代替外观验收。

节点增量布局、DisplayList 分块缓存及零拷贝专项验证继续按用户此前安排留待后续。
