# 参考图驱动的视觉与平铺主线

日期：2026-09-26。状态：0.1.0-5 BSP/玻璃与 0.1.0-6 运行时主题已现场验收；0.1.0-7 视觉收尾已安装，四主题物理截图通过，用户已现场确认外观及主要点击正常。

本计划承接 Skia 应用迁移和 Pi deb 演示。此前 0.1.0-4 的“画面正常”仅确认显示链路。本轮按参考图完成静态图标玻璃主题及 BSP 并部署 0.1.0-5，用户确认“外观正常，以上点击都正常”；具体验证范围见第 6 节。

## 1. 参考范围与目标

参考播放器画面内部桌面区域的玻璃顶栏、悬浮图标 Dock、柔和边缘与层次。保留当前壁纸，不复刻 VLC 标题栏、播放器控件或图中人物内容。

- Topbar：薄玻璃面板，左右控制区，时钟相对整个栏真正居中；窄屏时两侧内容让位，不能挤走时钟。
- Dock：底部居中的悬浮圆角面板，与屏幕边缘有距离；分割线、真实图标卡片、运行指示和悬停反馈。当前只提供已实现的 Music/Pref 入口；应用抽屉留待功能接入。
- 应用窗口：采用 i3/Sway 式容器树分割；支持横向、纵向、嵌套、焦点与工作区。窗口间留缝，边框、圆角、内阴影与外阴影形成层次。普通模式的窗口不互相任意覆盖，拖拽改变拓扑或分割比例。
- Shell 不进入应用平铺树；工作区可用范围依据 Shell 的实际布局与保留区域统一计算。
- 首版主题建议：Topbar 高 30–34 逻辑像素、边缘留白 8–12；Dock 图标 44–48、面板高 64–76、底部留白 10–14；应用 inner gap 10–14、outer gap 12–16、圆角 10–12、边框约 1。这些是待实机校准的主题参数，不能成为 WM 中散落的常量。
- 窄屏 Dock 首版使用明确的 overflow/滚动策略；不能逐项裁短图标。图标、文字与点击区域均需适配当前 1024×600 输出。

下表保留视觉改造前的差异审查，不能作为本轮代码的当前状态；新实现检查点见第 5 节。用户本次附件是目标图，并非当前屏幕截图。

| 范围 | 当前实现 | 需要补齐 |

## 3. 效果职责与解耦边界

### 客户端 SDK / Skia

DSL 属性解析、主题 token 解析、Scene 状态、测量与布局、文字/图标/控件、客户端自身图形的描边与阴影由 SDK 完成。效果按总体架构第 13–14 节进入独立 EffectState/Layer 语义，不在每种 geometry 或应用里重复实现。Skia 负责客户端本地效果回放。

主题使用一份定义产生客户端与 WM 所需的类型化配置；WM 不引入客户端 DSL/parser。使用相同参数名称、单位和版本，明确谁负责绘制每一种边框/阴影，避免 client 与 WM 重复叠加窗口框架。

### WM / compositor

WM 负责真实窗口树、Shell 放置、work area、surface 分层、焦点、装饰和跨 surface 背景效果。真实毛玻璃需要读取该区域下面的已合成内容，独立客户端的 Skia framebuffer 没有这些像素；模糊客户端自己的内容不能实现这一目标。

SDK 将已经解析并布局完成的 backdrop 需求转为平台层类型化请求，至少包含 surface 内区域、圆角、模糊尺度和提交关联。首版支持圆角矩形区域；WM 只接收效果数据，不接收 AST、控件树、应用动作或 DisplayList。私有 Wayland 扩展需单独定义版本、单位、能力协商和随 surface commit 生效的生命周期。

合成顺序：该效果区域下面的场景 → 扩展采样边界 → GPU 背景模糊 → 按圆角区域裁剪 → 客户端半透明 tint 与前景。不能采样本 surface 或更上层 surface。应用自身有不透明内容时，该内容仍会遮住下层材料，这是正常语义。

原生 `wlr_scene` 场景节点不能仅凭新增一个 `blur_radius` 字段完成上述流程。需要明确的 compositor GPU effect pass / 场景回放集成点，并验证导入、buffer 寿命与同步；不将客户端 Skia 和 DSL 搬回 WM。首版不默认替换 wlroots 版本，若需要修改依赖，先记录改动范围与维护成本。

窗口外阴影由窗口装饰层绘制在 tile 之外但不改变树的槽位；邻接间距、装饰绘制范围与输入命中区域需区分。圆角处客户端内容和输入区域应与可见轮廓一致。客户端局部卡片阴影则由 Skia 绘制；跨窗口 blur 与局部滤镜分别建模。

## 4. 执行顺序与完成条件

用户随后明确要求恢复统一启动与前端可控的平台目标。先完成 [LAUNCH_RUNTIME_RESTORATION_PLAN.md](LAUNCH_RUNTIME_RESTORATION_PLAN.md) 的包/host/预热服务与五应用切换门槛，再依次执行本节的视觉和平铺步骤。

### 第一步：统一真实窗口几何与 BSP

真实 XDG view 与纯窗口管理模型建立稳定映射，不伪造共享内存客户端或旧 IPC channel。map/unmap/destroy、焦点、工作区、关闭与 fullscreen 都更新同一窗口记录。TreeEngine 的目标几何驱动 configure，已提交的客户端尺寸与动画显示几何分别跟踪。

Shell 布局、保留空间与应用 work area 共用类型化配置。接通真实窗口的横/纵分割、嵌套、方向焦点、swap 和工作区可见性，删除按 view 数量横向均分的布局路径。普通单窗口的 gap 由主题决定，显式 fullscreen 的保留空间/装饰策略单独定义。

验收：2/3/4 个真实客户端可以嵌套分割，IPC tree 对应实际 surface；Shell 不占树节点；窗口不覆盖 Topbar/Dock，不出现旧模型和真实 view 的双焦点。

### 第二步：透明与通用布局契约

制定并实现 alpha 清屏、预乘格式、透明/不透明区域声明与圆角裁剪；同步修正 CPU 诊断目标，避免测试契约与 GLES 分歧。随后补足 measure/arrange、主轴/交叉轴对齐、flex、inset、intrinsic 与 overflow。文字布局要使用 shaping 的实际度量，不能仅用字号乘常数估计所有内容。

验收：圆角外真实透出壁纸，没有黑色矩形；时钟全栏居中；窗口变窄时内容遵循明确的溢出规则。

### 第三步：本地视觉与控件

按 Schema → Style/Effect → RenderTree → DisplayList → Skia 的顺序增加描边、内/外阴影、圆角 clip、图片 fit 和图标资源，再实现 IconButton、Separator、Progress/Slider、Toggle 的布局、绘制、命中与状态更新。图标和交互能力归 SDK，业务动作归应用。

本轮控件检查点包括 IconButton、Separator、Progress 和 Toggle；Slider 尚未接入，不能将本节全部长期目标标记完成。

验收：五个应用共享这些能力；无应用名分支；图标不是文字缩写/emoji 替代；控件状态与点击/键盘交互一致。

### 第四步：真实背景材料与窗口装饰

定义 surface effect 请求契约，接入 GPU backdrop pass、圆角窗口边框、顶缘高光、内阴影和外阴影。先验证静态 Shell 与真实窗口，再处理 resize/移动/下层内容变化产生的模糊区域更新。效果关闭时正常合成路径仍正确。

验收：保持背景细节的磨砂效果；下层内容变化会更新；窗口轮廓、阴影和命中一致；Pi 客户端与 compositor 都使用硬件驱动。模糊参数依据实测选择，不将历史 `passes: 4` 当作性能保证。

### 第五步：按参考图重排 Shell 和示例

统一主题 token，更新 Topbar、Dock 和示例模板。Dock 接入真实窗口列表/激活结果，不再把成功 spawn 次数当成全局运行状态。保持当前壁纸；桌面临时标题卡片按最终桌面布局规范移除。动效在基础布局/命中完成后接入，共用时间调度。

验收：1024×600 下左右状态区、时钟、图标和 Dock 留白正确；窗口拓扑仍符合平铺规范。保存同一输出尺寸的实际截图供参考图比较。

### 第六步：更新 deb 并重复实机验收

测试和捕获工具留在 `tests/`，不安装到生产目录。更新 deb 版本，验证安装资源和重启清理，再检查普通/聚焦窗口、分割、输入、缩放与玻璃效果。记录真实外观及性能数据；阶段完成状态分别标注，不能以映射成功代替外观验收。

节点增量布局、DisplayList 分块缓存及零拷贝专项验证继续按用户此前安排留待后续。

## 5. 本轮主题与五应用实施规范

本轮按用户确认的方向实现静态布局、图标、玻璃 tint、边框与阴影。图标为主，文字用于标题、状态与辅助说明；不加入放大、弹跳、转场等动画。当前壁纸保留。

### BSP 操作

| 输入 | 行为 |
| --- | --- |
| Super+B / Super+V | 在当前焦点设置横向/纵向分割；新窗口进入该分割 |
| Super+方向键或 H/J/K/L | 移动焦点 |
| Super+Shift+方向键或 H/J/K/L | 交换窗口位置 |
| Super+1..9 | 切换工作区 |
| Super+Shift+1..9 | 将当前窗口移到指定工作区 |
| Super+F | 进入/退出当前窗口全屏；全屏隐藏 Topbar/Dock |
| Super+Shift+Q | 请求客户端关闭窗口 |
| Super+左键拖动 | 落在中心交换，落在边缘形成分割 |

首版拖动改变窗口拓扑，实时拖动分割比例留待后续。IPC `split`、`focus`、`swap`、`workspace`、`move_workspace`、`fullscreen` 与 `close` 操作同一真实窗口树。有效提交尺寸通过 `wlr_xdg_surface_get_geometry()` 获得，不要求外部客户端显式设置 window geometry。

上表记录已接入的操作，不代表每个键盘组合均已现场逐项验收；本轮已测范围以第 6 节为准。

### 单一主题源与几何

当前源码以 `resources/themes/<id>/theme.prism` 为唯一主题源，删除旧 JSON、Python 常量生成器和生成头路径。纯主题编译器与应用编译器共享词法/语法实现，产生纯值 `ThemeSnapshot`；统一 launcher 向 WM 与既有 host 分发快照，按 ACK 完成通知或恢复。客户端 DSL 保留 `"@tokenName"` 引用，并以 `material: "window"` / `"panel"` 等语义材料取得样式；主题切换不重建业务模块或丢失绑定。未知 token、类型不匹配或非法数值报错。WM 只接收几何/装饰快照，不读取 DSL、AST、控件或 DisplayList。规范见 [DSL_THEME_RUNTIME.md](DSL_THEME_RUNTIME.md)，包语法见 [THEME_AUTHORING.md](THEME_AUTHORING.md)。

首批主题为 `glass`、`translucent`、`transparent`、`square`，分别组合磨砂、半透明、全透明与直角效果，不在 SDK/WM 按主题 ID 分支。四包保持相同几何；当前热切换拒绝改变 Layout，待配置/提交感知事务完善后开放。

当前基础尺寸：Topbar surface 保留 52，面板高 32、内缩 10；Dock surface 保留 100，面板高 76、底部留白 12，surface 请求宽 620；普通窗口 outer gap 14、inner gap 12、圆角 12。manifest 中窗口尺寸是初始请求，Shell 的实际几何与工作区由共享主题契约决定。客户端局部卡片及 Shell 面板绘制自身边框/阴影；普通窗口外围装饰归 WM，客户端不叠加第二套窗口外框。

### 五应用约束

| 应用 | 本轮模板与业务状态 |
| --- | --- |
| Desktop | 保留当前 PNG 壁纸，使用 cover 裁切；移除临时桌面标题卡片及对应业务绑定 |
| Topbar | 圆角玻璃面板，左右图标与真实系统状态，时钟以面板中心锚定；窄屏时侧区裁剪，不移动时钟中心 |
| Dock | 居中悬浮面板，两个真实入口 Music/Pref；使用向量图标、辅助名称和细运行指示，不添加未实现的 Apps/Files/Term 功能入口 |
| Music | 图标导航、播放/暂停及上一首/下一首、可见进度条；保留真实模块状态绑定。此业务仍是演示曲库与模拟播放进度，未实现音频解码/输出 |
| Settings | CPU/内存图标与真实 `/proc` 指标、进度条、刷新按钮；四个外观入口请求全局主题包，由 Current/Applied/Rejected 事件更新状态。删除业务模块中的局部配色；没有主题服务时明确显示不可用 |

Dock 的细运行指示依据平台订阅的已映射普通实例计算，并按 app ID 归并；重复事件不会多计，同一应用还有其他实例时关闭一个实例不熄灭指示。成功创建请求与真正展示/激活的反馈仍分开显示，保留 `Opening`、`ready`、`active` 或失败结果。

图标由 SDK 的通用向量资源回放，应用只引用资源名；不使用 emoji 或字母缩写假装图标，不在业务模块中加入 Wayland/EGL/Skia 绘制。`IconButton`、`Progress`、`Toggle`、`Separator` 以及布局/阴影都是通用 DSL 能力。

模板需要覆盖当前输出的两窗、四窗与四列尺寸：应用以 482×420、482×204、244×420 逻辑像素检查主操作可见与命中。Music 的封面区域与 Settings 的指标卡使用 flex 分配剩余高度，主操作保留固定点击区；较窄窗口的长曲名与指标说明明确裁剪，不能把控件移到 surface 外。Dock 辅助状态列使用 flex 并裁剪文字，优先保留两个完整图标入口。Topbar 时钟使用排版后的 intrinsic 宽度居中，不能只将固定宽度文本盒居中。

`client_app_templates_test` 除了解析模板，还将五个真实业务模块接到模板的类型化 binding schema，验证初始化、状态更新和按钮命中；测试代码不进入生产安装。数值进度采用 0–1，Toggle 使用布尔值，颜色以 ABI v1 新增 kind 的 `0xRRGGBBAA` 直通值投递，现有结构尺寸和旧模块回调保持兼容。

### 背景材料与验收状态

客户端请求 `backdropBlur` 后，只绘制自身半透明 tint 和前景；WM 必须读取该区域下层场景并完成真实 GPU 背景采样与模糊。客户端不重复读取壁纸并制作假模糊。透光区域、圆角、阴影外扩与输入区域须在同一坐标/提交语义下验证。

0.1.0-5 已部署五应用模板、Dock 实例分组、当时的 Settings 局部外观、SDK 通用布局/图标/控件/透明效果、真实 XDG view 与 TreeEngine 的映射、私有 surface-effect 协议及 compositor GLES 背景材料路径。后续源码新增 DSL 主题包、Scene 引用/材料更新、WM 快照与统一会话协议，Settings 当前模板已改为全局选择入口；新增能力已通过 28/28 CTest、真实 V3D 统一会话测试及 0.1.0-6 的实机切换/点击验收。客户端仍使用 Skia GLES，WM 的背景 pass 不链接 Skia 或客户端 DSL。

代码层 BSP 已支持横/纵嵌套分割、方向焦点/交换、工作区切换/移动、关闭与显式 fullscreen；Shell 不进入普通窗口树。Super + 鼠标拖放改变树拓扑或交换 tile，拖拽实时调整分割比例仍待后续实现。当前静态主题无新增转场、放大、弹跳或移动动画。

2. Dock 按「应用中心｜固定应用｜运行应用」分段，分隔线划分。应用中心固定在最左侧，本阶段点击不展示界面。固定段保留 Music/Preferences；右段按真实实例事件归并两个 demo 的运行状态，关闭最后一个实例后收起该图标。运行图标下使用与 Topbar 一致颜色/厚度的横线，删除文字标签和 Active/launch 状态文本；启动待定/失败以图标反馈，Accepted 仍不代表呈现或激活成功。
3. 通用 DSL `visible` 属性控制整棵子树布局、绘制、输入与背景效果，隐藏后不保留间距；Scene 节点与业务绑定保留。此能力属于 SDK，不以 Dock/app 名称分支实现。
4. 四主题保持相同 ThemeLayout。Glass 使用烟灰 tint 降低白色蒙层，白色前景与彩色图标保持对比；卡片/控件/Dock 图标底座使用主题材料的内外阴影。直角/全透明等效果组合仍由各自 DSL 包控制，窗口根不重复绘制 WM 外阴影。
5. Music 调整为紧凑标题、视觉封面、主副标题、进度/时间及图标控制；Preferences 调整为紧凑指标、进度条与四个图标主题选择，当前选择由已确认的 ThemeEvent 表示。布局必须在 482×420、244×420、482×204 下保留操作区域，不以 clip 掩盖不可点击按钮。
6. 构建后检查模板/业务绑定、隐藏与恢复、运行分组/启动门槛，保存真实 V3D 截图。生产包不包含测试或捕获工具；重打 deb 并做 Pi 现场确认。

本轮不添加 Dock 放大、弹跳或横线动画。颜色、横线厚度、图标尺寸、材料和间距写在主题包中；底层只提供通用能力。本节为执行要求，完成记录在验证后追加。
